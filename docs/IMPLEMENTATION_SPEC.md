## 1. 产品目标与不可妥协项

### 1.1 要实现的不是普通带壳截图

设备必须是真实三维几何体。旋转到斜侧面，能够看到机身厚度、中框、倒角、按键以及背部主要结构；高光、反射与投影随着模型、相机和光源的相对位置合理变化。

以下实现不算合格：

- 仅对正面 PNG 做透视变换、CSS 旋转或 Android Canvas 仿射变换。
- 把商品图中的固定高光和阴影直接贴到机身上。
- 用一个通用圆角长方体，换个“小米”名字就作为最终模型。
- 只在 Blender 中做出漂亮渲染，而 Android 内只展示低质替代物。
- 导出 Android 预览区域的屏幕截图，然后拉伸成所谓“4K”。

### 1.2 首版完成定义

首版必须同时具备：

1. 至少一个经过资料比对的小米折叠机模型，含外屏合拢和内屏展开两种状态；若确实无法核实目标机型，按第 6 节降级并如实标记。
2. 从系统选图器导入截图，截图文字清晰、比例正确，不自动拉伸。
3. 真正的三维 yaw / pitch / roll 调整，以及缩放、平移和重置。
4. 至少三套能看出区别的光影预设，以及反射强度、灯光方向和阴影控制。
5. 实色 / 渐变背景；透明 PNG；实际目标分辨率渲染的 PNG 输出。
6. 草稿自动保存，横竖屏与折叠展开后的编辑状态保持。
7. 可安装 APK、可复现构建、可再生成模型和真实测试记录。

“功能存在”与“已经验证”必须分开记录。未测试不得写成通过。

### 1.3 视觉优先级

**屏幕内容清楚 > 外观轮廓准确 > 中框与玻璃质感 > 构图与阴影 > 背面微细节 > 外围功能数量。**

这是摄影式外观重建，不是工业 CAD 复原。未公开的毫米级结构允许合理估计，但必须留下来源、置信度与近似标记，不能伪装成原厂模型。

同一问题最多进行三条实质不同的排查或替代路径，记录结果。之后隔离该问题，继续其他可完成任务。可以交付标注限制的阶段版本，但不得把未达标项目改写成已完成。

资料不足可用明确标记的近似模型验证闭环；不能因为有了近似模型就删除正式机型重建任务。

## 4. 技术栈与工程边界

### 4.1 默认选择

| 层 | 默认实现 |
|---|---|
| Android UI | Kotlin、Jetpack Compose、Material 3；简体中文为主，字符串集中管理 |
| 状态 | ViewModel + StateFlow，编辑状态使用不可变数据模型 |
| 渲染 | Filament Android、gltfio、filament-utils；优先 OpenGL ES 后端验证，Vulkan 不作为首版硬性依赖 |
| 模型格式 | glTF 2.0 / GLB，机身常规 PBR 材质 + 独立可替换屏幕材质 |
| 本地存储 | JSON 工程文件、应用私有图片副本、DataStore 设置；首版不引入不必要数据库 |
| 图片导入 | Android Photo Picker；不可用时回退 Storage Access Framework |
| 保存与分享 | MediaStore 与临时授权 content URI；不依赖传统绝对文件路径 |
| 建模 | Blender Python；输入为显式参数及素材清单 |
| 构建辅助 | Python 跨平台脚本，Gradle Wrapper，版本目录 / 锁定文件 |
| 最低系统 | 默认 `minSdk = 29`，这是项目取舍，不是对 Filament 最低要求的声明 |
| ABI | 首要 `arm64-v8a`；模拟器根据宿主支持添加 `x86_64` 或 arm64 测试配置 |
| 网络 | 应用首版不需要 `INTERNET` 权限；开发工具联网与 App 运行时联网分离 |

### 4.2 依赖与工具链

选择实施时互相兼容的**稳定** Kotlin / Compose / Android Gradle Plugin / Gradle / JDK / SDK 组合，写入 `docs/TOOLCHAIN.md`，固定版本，不使用 `+`、浮动 nightly 或未经验证的 snapshot。

Filament 的 `filament-android`、`gltfio-android`、`filament-utils-android` 与 `matc` 必须采用匹配版本。`.mat` 源文件与编译命令要入库；`.filamat` 可以随构建产物提供，但不能变成不可追溯黑盒。

编译目标覆盖选定后端；不能只编译桌面材质变体后直接拿到 Android。`cmgen` 等工具也优先使用同一发布包。具体 CLI 参数和 Java / Kotlin API 以**锁定版本**文档与源码为准，不照抄记忆中的过时接口。

Filament 包含原生库；按 Android 官方方法检查 APK 中 `.so` 的架构、打包对齐与 16 KB 页面兼容性，不以“业务代码是 Kotlin”推断不受影响。[R20]

## 5. 官网资料检索：由 Agent 全权执行

### 5.1 检索目标

优先收集：正式产品名称、正面、背面、左右侧面、斜前方、合拢、展开、铰链特写、相机模组、官方长宽厚、颜色与材质描述。

首轮搜索可使用：

```text
Xiaomi 18 Fold 官网 参数
site:mi.com Xiaomi 18 Fold
site:mi.com 小米 折叠屏 概述 参数
Xiaomi 18 Fold official dimensions front side unfolded
```

搜索词只是入口。**必须打开实际页面核对标题、正文、图片和商品身份，不能把搜索摘要当作已确认参数。**动态商城可能返回错误商品、重定向或过期缓存；`product_id` 不是充分证据。

### 5.2 来源优先顺序

1. 小米官方网站实际产品概述页、参数页、官方商城图片和发布资料。
2. 可验证的官方媒体资料、官方发布账号、官方视频中的清晰产品视角。
3. 仍然不足时，使用有出处的第三方评测照片仅辅助理解外观，并单独标记。

域名在官方体系内不意味着内容一定由厂商发布：社区用户帖不能自动升级成官方参数证据。渲染图、实拍照片、宣传概念图要分别标记。

### 5.3 自动取图方法

优先读取公开 HTML 中的 `img`、`srcset`、懒加载字段、CSS 背景图和页面初始化 JSON。动态站点允许使用 Playwright / 浏览器读取**公开页面正常加载**的资源请求，提取原始分辨率图片地址。

仅下载当前机型相关资源，限制并发和重试，验证 MIME、图片解码、尺寸与 SHA-256。不要全站抓取，也不要从私人会话、账号接口或需要越权的地址拿资料。

遇到防盗链，可携带公开页面合法的 Referer；遇到登录、验证码、频率限制则停止该路径并换来源。不要破解限制。

先输出参考图联系表，辨认每张图的视角和用途。不要默认依赖 OCR 解析复杂商品长图；尺寸优先读取文本。确需从图中测量时，记录截图位置和人工 / 视觉测量方法。

### 5.4 资料台账

每个资料项至少保存以下字段；URL、路径和哈希由实际下载填充，不允许虚构：

```json
{
  "sourceId": "official-front-001",
  "publisher": "Xiaomi",
  "pageUrl": null,
  "assetUrl": null,
  "retrievedAt": null,
  "localPath": null,
  "sha256": null,
  "view": "front_closed",
  "sourceType": "official_product_render",
  "verifiedProductIdentity": false,
  "usage": "local_visual_reference_only",
  "redistributionPermission": "not_verified",
  "notes": "待实际检索填写；此条是字段示例，不是已找到的素材"
}
```

保存 `sources.json`、`contact-sheet` 和 `research.md`。官网图片默认仅放本地参考缓存，不打入 APK、不上传公共仓库、不宣称可自由再分发。

### 5.5 尺寸可信度

将每个关键参数区分为：

- `official`：明确官方数值，并附来源。
- `measured`：从参考图测得，有基准尺寸、视角与方法。
- `estimated`：根据可见外形合理估计。
- `unknown`：暂无法判断。

官方尺寸有多个版本时，区分配色、材质、机身厚度是否含相机凸起、合拢 / 展开状态，不能混拼成一个不存在的机型。

## 6. 找不到完整资料时，不能停在“请用户提供模型”

按以下顺序继续：

**路径 A：目标机型资料足够。**按官方尺寸与多视角图生成 Xiaomi 18 Fold 外观模型，保留少量估计字段。

**路径 B：有足够外观图，缺少部分尺寸。**保留可核实尺寸，其余通过图像测量估计；应用机型信息中注明“外观重建 / 部分尺寸近似”，并继续完成套壳闭环。

**路径 C：目标机型身份或主要外观不能可靠核实。**不要擅自认定用户写错名称，也不要编造新机规格。生成“宽比例折叠机 · 近似模型”用于上述截图尺寸的功能测试；同时检索一个资料完整的小米折叠机作为第二个、真实具名的参考模型。两者不能混用名称。

**路径 D：联网完全不可用。**先用明确标记的参数化近似机完成 App、导出和测试；在报告中列出缺失官方资料及补齐流程。这是受限交付，不可写成“目标小米机型已精确完成”。

`verificationStatus`、`approximationNotes`、模型来源和名称须贯穿资料台账、运行时机型清单与最终报告。未知字段应由 Agent 作可追踪估算或保留限制，不能把 `null` 当作 0 毫米继续建模。

## 7. 从商品图建立真正可用的手机模型

### 7.1 固定生产路线

```text
公开资料 → 参考图筛选与尺寸台账 → 几何参数 → Blender 脚本
→ GLB 与机型清单 → glTF 校验 → 标准视角渲染 → 轮廓比对
→ Android Filament 材质校准 → 实际导出样张 → 修正参数并再生成
```

不要把单张图生 3D 当主路线。可以用它辅助理解体块，但不得依赖需要用户付费、登录或上传素材的服务，也不得未经修正直接使用带错误边缘、浮雕屏幕和错误拓扑的结果。

### 7.2 建模职责拆分

几何负责：机身比例、圆角、中框截面、边缘倒角、屏幕边界、按键、铰链、镜头凸起。

材质负责：金属 / 非金属响应、粗糙度、细微表面变化、玻璃反射。不能用照片中的固定高光冒充真实反射。

不建造芯片、电池、复杂铰链内部机构和看不到的装配结构。背面虽然不是主场景，仍需正确主要轮廓，避免自由旋转后露出一个无结构盒子。

### 7.3 参数化策略

用可控的圆角轮廓、挤出、截面与倒角生成机身；独立参数描述屏幕、背板、镜头和按键。对明显不同的机型使用专属组件，不把所有小米手机压成同一种外壳。

建议参数字段：

```text
closed_width_mm / closed_height_mm / closed_body_thickness_mm
open_width_mm / open_height_mm / open_body_thickness_mm
corner_profile / corner_radius_mm / edge_bevel_mm
frame_cross_section / frame_thickness_mm
outer_screen_rect_mm / inner_screen_rect_mm
screen_corner_profile / screen_cutouts
hinge_width_mm / hinge_shell_profile
camera_module_profile / camera_bump_mm / lens_layout
button_positions_mm / antenna_break_positions
material_variants / default_variant
```

研究资料和几何数值分开：`research.json` 保存证据与置信度，`geometry.json` 保存经验证可用于生成的有限数值。建立 schema、范围检查与单位检查。

若使用超椭圆或分段曲线拟合边缘，以实际参考轮廓为依据，不以“越圆越高级”为标准。平面圆角半径不等于金属截面的倒角半径。

### 7.4 统一坐标与尺度

运行时约定：右手坐标；`+X` 为正面向右，`+Y` 为正面向上，`+Z` 为屏幕正面朝外；原点在机身主体中心。未旋转相机位于 `+Z`，朝向原点。

资料与生成器可以用毫米；导出 GLB 与 Filament 使用米。毫米转米只做一次。Blender 默认轴向与导出坐标存在差异，必须通过明确转换和轴向测试验证，不靠试着旋转 90° 后“看起来对了”。glTF 坐标与单位遵循规范。[R14]

机身根节点缩放应用后再导出，保留语义节点和法线。检查负尺度、法线朝向、UV 镜像、阴影包围盒与裁剪平面。

### 7.5 模型语义节点合同

两种状态分别输出 GLB，首版不实现连续变形。以 `device.json` 显式声明节点映射，不依赖 glTF 内部数组索引或模糊名称搜索。

```text
device_root
├── chassis_main
├── chassis_secondary          # 折叠双机身；结构按实际情况组织
├── frame_main
├── back_panel
├── hinge_shell
├── buttons
├── camera_module
├── screen_outer_content       # 在该状态中实际存在才声明
├── screen_outer_glass
├── screen_inner_content       # 在该状态中实际存在才声明
└── screen_inner_glass
```

上面是语义，不要求所有模型都有全部节点。`folded.glb` 声明外屏节点；`unfolded.glb` 声明内屏节点。若保留背面的外屏，单独指定为非活动屏幕，不要错误映射内屏截图。

建立自动检查：节点存在、屏幕实体唯一、材质槽可替换、前法线正确、屏幕四角 UV 正确、两个状态都不缺资源。

### 7.6 屏幕模型

内容面与机身分离。屏幕真实轮廓可由圆角网格或经验证的遮罩实现，截图 UV 覆盖完整有效内容区域，不把圆角处文字拉伸到弧线上。

挖孔、黑边和玻璃属于机型外观层，不修改用户原文件。超出物理屏幕可见区域的内容允许被真实边缘遮挡，但不能额外、隐蔽地裁掉状态栏。

内屏完全展开时保持内容连续。首版折痕默认极弱或关闭；可以用轻微法线 / 粗糙度变化表现，不用明显凹槽切断截图文字。

### 7.7 首版资源预算：目标，不是已经测得的数据

- 每状态约 20,000–60,000 三角形为初始预算，超过 100,000 必须说明必要性。
- 尽量控制在 25 个以内的可见 renderable；避免为每个小装饰独立创建材质。
- 机身材质尽量参数化；非截图纹理通常不超过 2048 边长。
- 每状态 GLB 争取不超过 10 MB；不把多套高分辨率参考照片嵌入模型。
- 机型资源预算与引擎导致的 APK 体积分开报告。

不要为了降低面数破坏轮廓或倒角高光。精度优先集中在正面边缘、中框和可见铰链，隐藏面可以简化。

### 7.8 模型验收样张

每状态至少生成正面、左右 30°、俯视 20°、仰视 15°、侧面、背面七张；同时保留线框 / 法线诊断图。

对接近正视的参考图先对齐主体轮廓，再比长宽比、屏幕占比和圆角。只有可标定且可比较的参考图才报告数值误差；宣传透视图不能假装是正投影视图。

可测时以外轮廓归一化误差约 2% 为初始修正目标；未知结构写明近似。此数值是工程验收目标，不是声称能恢复工业 CAD 精度。

## 8. 渲染架构：截图清楚与真实光影同时成立

### 8.1 渲染职责

`core/render` 接收不可变 `RenderState`，负责模型、材质、屏幕纹理、灯光、相机和目标缓冲区。不得从 Compose 控件直接读取旋转角度，也不得在各个按钮回调里散落原生资源创建代码。

建议内部组件：

```text
RenderController         引擎与所有者线程、帧调度、生命周期
DeviceAssetLoader        GLB、语义节点、材质实例、错误与回退
ScreenTextureController  截图上传、裁切矩阵、颜色空间、资源替换
LightingController       环境反射、方向光、阴影与预设
CameraController         投影、构图、缩放与裁剪
ExportRenderer           冻结场景、离屏渲染、读回与清理
RenderDiagnostics        引擎版本、资源数、帧耗时和故障信息
```

`ModelViewer` 样例可用于第一步验证；最终产品应拥有自己的资源、导出与状态管理，不把业务永久塞进样例 Activity。[R03–R04]

### 8.2 机身材质

使用可解释的金属度 / 粗糙度工作流。中框、背板、镜头玻璃与屏幕边框分开，适当几何倒角形成真实边缘高光。不要用过强金属反射把所有机型都变成镀铬玩具。

使用高质量环境反射、适量直接光和柔和阴影建立摄影棚质感。Filament 的材质参数、环境照明与渲染模型参见官方文档。[R05–R06]

初始值只作为调试起点，不宣称是厂商真实物理测量：金属中框粗糙度可先试 0.22–0.38；非金属表面金属度为 0；镜头、屏幕玻璃采用较低粗糙度并控制反射强度。最终靠 Android 实际样张校准，不按参数“看起来专业”验收。

### 8.3 屏幕内容与玻璃反射

默认提供“清晰展示”模式：内容层使用自定义 unlit 材质或经验证的等效路径，避免截图像普通塑料一样在背光处变黑。玻璃反射以独立、低强度层叠加，需有正确深度测试、面朝向和视角变化。[R05]

注意：unlit 不等于自动原色。曝光、色调映射、输出转换和透明混合仍可能改变内容。必须用第 16 节的色卡测试确定实际误差。

推荐实施顺序：

1. 先完成无反射、无额外调色的内容映射，验证方向、色彩和边缘。
2. 再加入玻璃层或自定义可控反射材质，明确每层深度写入与混合策略。
3. 反射强度可以归零；默认较弱，不能用大片白色高光盖住主要文字。
4. 反射必须随视角 / 环境方向改变，不贴一条永远固定的白色渐变冒充玻璃。
5. 两层避免共面，偏移量根据实际模型尺度确定，避免 z-fighting、透视漂浮和边缘分层。

若复杂玻璃透射导致穿帮，首版采用无折射的表面反射近似。不要为了“物理正确”引入文字位移、双影和显著色偏。清晰模式与更强反射的展示预设都必须共用同一截图原文件。

### 8.4 摄影棚环境与灯光

优先用脚本生成原创简洁摄影棚 HDR 环境：大柔光窗、条形补光、较暗背景。按 Filament 所需格式离线预计算，不把高分辨率 HDR 作为每次启动的运行时计算任务。

也可使用具有明确再分发许可的环境素材，但需保存许可证。首版不依赖不明来源 HDRI 包。

环境光负责反射氛围；直接光负责可控投影。两者方向应协调，不能让屏幕显示左侧柔光窗、地面却投出明显相反方向且不合理的主影。

至少提供：

| 预设 | 预期效果 |
|---|---|
| 柔光白棚 | 浅背景、柔和亮边、适量接触感，截图最清楚；默认 |
| 冷灰产品照 | 更明确的侧边高光、中等对比、柔和地面投影 |
| 深色边缘光 | 深背景、较强轮廓反射，仍能分辨机身厚度且不让截图过曝 |

控制项：灯光方位、整体强度、环境旋转、反射强度、阴影强度 / 柔化。不要给用户暴露几十个没有解释的材质底层参数。

### 8.5 地面、浮空与透明阴影

默认提供“浮空”和“落地”两种场景：

- 浮空：轻微悬离地面，允许自由三轴旋转；阴影由实际场景生成。
- 落地：根据变换后的机身最低点调整相对地面位置，避免设备穿地；旋转时地面本身不跟着设备翻转。

透明 PNG 的阴影接收平面不能变成灰色矩形。Filament 文档提供 unlit `shadowMultiplier` 透明接影方案，且明确限制为**方向光阴影**。首版透明接影优先走这条已知路线，不假定点光 / 聚光直接适用。[R05]

AO 只能辅助接触感，不能代替设备随姿态变化的真实投影。软阴影算法和具体参数由锁定版本能力选择，优先稳定；不默认开启所有昂贵效果。

### 8.6 相机与三维操作

保存设备四元数，不把持续手势累积为易万向节锁的 Euler 角。面板仍可显示 yaw / pitch / roll，转换规则保持一致。

默认旋转设备根节点，摄影棚灯光和地面固定；不要同时又旋转相机又旋转设备，造成手势方向混乱。用相机距离 / 焦距控制视角，以构图偏移控制平移。

初始透视可采用约 35° 的垂直 FOV；这是设计默认值，允许在合理范围内调整。正面预设可提供正交模式，减少测量与展示的透视误差。

所有预设自动适配模型包围盒。根据视口比例计算安全边距，不用固定相机距离适配所有机型。缩放和极端角度要防止近裁剪面切穿机身。

### 8.7 线程、生命周期和原生资源

引擎与资源操作限定在一个所有者线程。默认可沿官方 Android 样例采用主线程帧调度；磁盘读取、图片解码、文件编码放到后台。不要把 Filament API 随机放进 `Dispatchers.IO` 并发调用。

截图快速替换使用递增任务代号，旧解码结果不得覆盖新选择。上传 / 读回使用的 Buffer 在回调完成前保持有效引用。避免双重释放由 gltfio 管理的资源。

配置变更、前后台切换与 Surface 重建时：先停止帧调度并正确解绑，再按锁定版本所有权规则释放或重建渲染资源；编辑状态留在 ViewModel / 草稿，不依赖旧 Surface 或旧 Engine。

静止场景按需渲染；有时域累积时在达到稳定帧数后停止连续刷新。后台不持续占用 GPU。连续切换模型和导出后，资源计数应回到稳定范围。

## 9. 截图导入、映射与色彩

### 9.1 导入流程

优先使用系统 Photo Picker；无可用组件或无 Google 服务时回退 SAF，不强制安装 GMS。使用系统授权内容 URI，避免索要整库访问权限。[R15]

本工具处理用户主动导入的截图，不自动读取其他应用屏幕，不依赖 MediaProjection、无障碍服务或悬浮窗权限。

选图后校验 MIME、文件大小、可解码性和像素尺寸；处理 EXIF 方向。对超长图、大图采用采样解码和资源限额，不能一次性解码导致 OOM。

为了可靠恢复草稿，默认将用户主动选择的单张原文件复制到应用私有工程目录。复制失败时给出明确错误；不让短期 URI 权限成为草稿长期可用的唯一前提。删除草稿同步清理其私有副本，不能删除用户相册原图。

### 9.2 屏幕状态推荐

按**图像方向校正后的**宽高比与机型清单匹配。先精确分辨率提示，再比较长宽比；分辨率只能帮助选择屏幕状态，不能证明图片来自某个机型。

目标测试：

- `1168 × 1712` → 优先推荐已匹配的外屏状态。
- `2364 × 1672` → 优先推荐内屏横向状态。
- `1672 × 2364` → 推荐内屏竖向构图；默认不把文字直接旋转成横倒。

在多个状态同样匹配或比例明显不符时，保留当前机型，使用“完整显示”，界面显示非阻塞提示并允许一键切换。不要弹出要求用户才能继续的调研式确认。

机身物理屏幕比例与上述测试图片不一致时，尊重模型比例并使用适配策略；不要拉宽机身使其假装符合官方尺寸。

### 9.3 适配策略

支持两种主要模式：

- **完整显示（默认）**：保持比例，必要时留边，默认留边使用屏幕黑色。
- **填满屏幕**：等比放大裁切，可拖动调整裁切位置，提供居中重置。

不要提供默认开启的非等比拉伸。截图已经包含的系统状态栏和导航栏原样保留；不伪造系统图标，不重复添加状态栏。

在统一屏幕坐标下，设图像尺寸为 `Wi, Hi`，屏幕目标矩形为 `Ws, Hs`：

```text
fitScale  = min(Ws / Wi, Hs / Hi)
fillScale = max(Ws / Wi, Hs / Hi)
drawnW = Wi * scale
drawnH = Hi * scale
offsetX = (Ws - drawnW) / 2 + panX
offsetY = (Hs - drawnH) / 2 + panY
u = (screenX - offsetX) / drawnW
v = (screenY - offsetY) / drawnH
```

`panX/panY` 必须限制在对应模式的有效范围。屏幕坐标、图片坐标和 glTF UV 的 Y 方向通过带四角标签测试图确认，避免 EXIF、解码和 shader 重复翻转。公式本身不规定最终 GPU 纹理原点。

映射尽量在 UV 变换中完成，不为每次拖动重新编码整张图片。导出时重新使用足够分辨率的源图，而不是永久复用预览降采样纹理。

### 9.4 色彩与透明像素

首版导出统一为明确的 SDR / sRGB 结果。对于广色域或 HDR 输入，明确执行转换或给出非阻塞提示，不静默宣称保留 HDR。

按选定引擎的纹理格式和材质读取方式处理 sRGB 到线性转换，避免解码器和 shader 重复 gamma 校正。颜色纹理与法线 / 粗糙度等数据纹理不能使用同一种颜色空间规则。

调试阶段保留标准色卡、灰阶、细文字、棋盘格和四角编号输入。清晰模式关闭反射和额外调色后进行数值比对；成片模式允许光学表现，但应保留可回到清晰模式的入口。

## 10. 编辑器与折叠屏交互

### 10.1 界面目标

简洁、精致、以预览为中心，不做庞杂的 3D 软件。采用中性灰基础界面和克制强调色；首版 UI 不需要复杂实时毛玻璃，避免为装饰牺牲预览性能。

启动直接进入编辑器。未导图时显示原创示例截图与明确“导入截图”按钮，不显示空黑屏。导入后少量操作即可得到好看的默认成片。

### 10.2 布局

小窗口：顶部为返回 / 撤销 / 重做 / 导出，中央为可操作预览，底部紧凑工具栏与可展开属性面板。

大窗口：预览占主要空间，属性面板在右侧；是否常驻机型栏由实际可用宽度决定，不为了“三栏”硬塞狭窄界面。

按 Android 窗口尺寸类和 dp 决定布局，不按物理像素、设备型号字符串或简单 `isTablet` 判断。折叠 / 展开、分屏和旋转可能改变可用窗口，编辑内容必须连续。[R16]

推荐属性入口：**设备、角度、光影、背景、画布**。常用控制常驻，高级材质参数不放首页。

### 10.3 手势约定

| 操作 | 行为 |
|---|---|
| 单指拖动预览 | 绕中心旋转设备，直觉方向、有限惯性 |
| 双指捏合 | 等比缩放构图 |
| 双指平移 | 调整画布内位置 |
| 双指扭转 | 调整 roll；若与平移 / 缩放冲突，先提供角度滑杆并保证可靠 |
| 双击设备 | 适配画布并复位平移，不清空截图 |
| 面板“重置角度” | 只重置姿态 |
| 全局“重置” | 撤销可恢复的场景重置，不删除源图 |

在裁切编辑模式中，拖动作用于截图位置而不是机身旋转；退出后恢复正常手势。手势区不能与面板滚动争抢。

### 10.4 首版预设与控件

角度至少提供：正面、左前、右前、俯视、横放；再提供 yaw / pitch / roll 精调、焦距 / 透视强度、适配画布。

背景至少提供：透明、纯白、浅灰、深灰、双色渐变、自定义颜色。画布至少提供 1:1、4:5、9:16、16:9 和自定义宽高。

机型状态明确显示“合拢 · 外屏”“展开 · 内屏”，与编辑器所在手机是否折叠分离。用户展开自己的手机不应自动把作品的模型状态改掉。

控件用 dp / sp，触控目标至少按 48 dp 设计；支持合理字号放大、系统安全区域和系统深浅色。不要仅在固定模拟器截图上看着正常。

### 10.5 空态、异常与反馈

模型加载失败可切回可用模型并保留工程；截图失效可重新导入但不能崩溃；导出显示进度和取消；保存成功显示目标相册与分享入口。

无功能的入口先不显示，不以“即将上线”按钮填充界面。权限拒绝、存储空间不足、显存不足、文件损坏均需可理解反馈。

## 11. 状态模型与工程保存

### 11.1 单一事实来源

预览、缩略图、导出、撤销重做都从同一份 `ProjectState` / `RenderState` 派生。不能分别维护一套 UI 角度、一套模型角度、一套导出角度。

以下是本项目接口概念，不是 Filament 已存在的 API：

```kotlin
interface MockupRenderer {
    fun applyState(state: RenderState)
    suspend fun export(request: ExportRequest): ExportResult
    fun pause()
    fun resume()
    fun close()
}
```

`applyState` 需要内部线程派发与合并；`export` 捕获独立状态快照；`close` 幂等，正确处理尚未完成的资源回调。

### 11.2 工程字段

```text
schemaVersion / projectId / createdAt / modifiedAt
sourceImage: privateRelativePath, originalSize, orientedSize, contentHash
asset: deviceId, assetVersion, assetHash, stateId, materialVariant
screenMapping: fitMode, cropOffset, sourceRotation, uvTransform
pose: quaternion, compositionOffset, zoom
camera: projection, verticalFov, framing
lighting: presetId, environmentRotation, intensity, reflection, shadow
background: mode, colors, gradientAngle
canvas: aspectRatio, requestedOutputSize
quality: previewTier, exportTier
```

持久化相对路径，不把用户真实绝对路径、相册名称或私人元数据写入可公开日志。

采用版本化 JSON、原子写入和迁移函数。保存暂存文件成功后替换旧文件；崩溃不能同时损坏源图与唯一工程副本。

### 11.3 撤销、自动保存、恢复

一次连续手势或滑杆拖动只记录一个撤销动作，避免每帧污染历史。至少保留 30 步内存历史。

对编辑变化进行节流保存；进入后台时补一次保存。旋转、折叠、Activity 重建恢复完整场景，进程死亡后可恢复最后已保存草稿。

导出中的状态冻结；用户继续拖动不会污染正在生成的图片。模型版本更新后对旧工程进行兼容映射，不直接读取已经失效的节点索引。

## 12. 高清与透明导出：必须是真正离屏渲染

### 12.1 输出合同

默认输出 PNG，长边 2560 px。另提供 2048 和 3840 px 级别，以及受设备能力约束的自定义尺寸。支持 `2160 × 3840`、`3840 × 2160` 等真实目标尺寸，不把“长边 3840”混称为所有情况下相同的 4K 格式。

实际输出必须与用户选择一致；不支持时显示可用最大值。不得静默降分辨率后仍标成原尺寸，也不得把低分辨率预览放大。

首版不强制 JPEG、8K、动画或批量导出。PNG 必须支持带背景和透明两种模式。

### 12.2 渲染步骤

1. 在渲染所有者线程捕获不可变状态快照，验证源图、机型、目标尺寸与存储空间。
2. 暂停或协调预览渲染，创建目标分辨率的颜色 / 深度附件与 RenderTarget；配置对应 View 和正确投影。
3. 加载足够分辨率的屏幕纹理，等待模型 / 纹理上传完成，避免第一帧黑屏或旧截图。
4. 按所选抗锯齿路径渲染；需要时域累积时必须以受控帧数稳定后读回，不能偷取未稳定帧。
5. 按锁定 Filament 版本的要求使用 `readPixels` 或等效路径读回。颜色附件用途、帧调用顺序、回调和 Buffer 生命周期必须正确。[R07]
6. 校验 RGBA 通道、Y 方向、颜色空间与 alpha 表示，在后台编码 PNG。
7. 通过 MediaStore 原子完成保存；失败时清理未完成条目，提供重试。
8. 在所有者线程清理导出资源，恢复预览资源和质量设置。

Filament 官方说明读回开销显著。因此本路径用于用户触发的静态图片导出，不用于逐帧预览或未规划的视频录制。[R07]

### 12.3 透明背景与 alpha

透明模式要求：清屏 alpha 为 0、背景 / skybox 不写入不透明底色、View 与目标混合策略正确、玻璃和接影材质可正确输出透明度。

**PNG 的 RGB / alpha 与 Android Bitmap 的预乘表示不能混淆。**实测当前读回缓冲的含义，确保送入编码器的表示匹配。需要解预乘时必须正确处理 `alpha = 0`；不要盲目反复预乘 / 解预乘。

用同一张透明图叠到白、黑和彩色背景检查：没有黑边、白边、灰色矩形底板和错误颜色。透明地面阴影按第 8.5 节实现；若带阴影导出尚有缺陷，可先保留正确的“透明、无地面阴影”模式，同时把带阴影模式标记未完成，不能假报全功能验收通过。

### 12.4 抗锯齿与细文字

优先选择经过实际测试的 MSAA / FXAA / 适度超采样组合。对文字敏感场景，时域抗锯齿造成的拖影和过软必须评估；不要同时堆叠所有算法。

屏幕纹理使用合适 mipmap 与采样策略，斜角下减少摩尔纹；高质量导出不沿用低清交互预览的纹理预算。预览与导出的差异只应来自分辨率和合理质量提升，不应来自另一套色彩或灯光逻辑。

### 12.5 内存预算与能力协商

`2160 × 3840 × 4` 的单个 RGBA8 缓冲约 31.6 MiB；深度、HDR 中间缓冲、抗锯齿、读回与 Bitmap 可能再占多份。不能只统计最终 PNG 文件大小。

导出前按输出尺寸估算 CPU / GPU 峰值，查询支持的纹理与 RenderTarget 能力，设置保守上限；导出队列首版单任务运行。OOM 时清理资源并提供较小尺寸重试，保持编辑工程完整。

切片渲染属于后续优化，不作为首版默认实现；否则需要额外处理投影、后处理、阴影和接缝一致性。

## 13. 性能、稳定性与隐私目标

以下为待测目标，不是对任意手机的性能承诺：

| 指标 | 首版目标与测试方式 |
|---|---|
| 交互帧率 | 目标真机 60 fps，重场景尽量不低于 30 fps；记录机型、GPU、系统、后端和窗口分辨率 |
| 静止耗电 | 画面稳定后停止不必要的连续帧；后台不持续渲染 |
| 预览质量 | 先用长边约 1600–2048 的内部预算；折叠屏大窗口实测后调整，不强制所有场景原生像素全分辨率 |
| 导出 | 3840 长边静态图片争取数秒完成；报告实测值，不预设“所有机型秒出” |
| 内存 | 统计 Java、native、图像缓存及可测的 GPU 资源；重复操作后应稳定，不持续爬升 |
| 生命周期 | 前后台 20 次、状态切换 30 次、截图替换 30 次、连续导出 10 次不崩溃 |
| 首次加载 | 有清晰的加载状态；离线可以使用已打包机型 |
| 权限 | 无默认联网、无整库访问强依赖、无联系人 / 定位 / 麦克风 / 相机权限 |

不把用户选图上传到外部服务；不加入统计 SDK。日志只记录尺寸、耗时、错误码和必要的内部标识，不记录图像内容和用户文件全路径。

开发测试使用原创合成截图，包含虚构文字、图形、色卡与明确的 TEST 标记，不使用用户私聊、通知栏隐私或账号页面。

## 14. 运行时机型清单与资产生产合同

### 14.1 `device.json` 必备字段

实现 JSON Schema 或等价校验。以下列的是字段合同，不是可以直接打包的含假参数样例：

| 字段 | 含义与约束 |
|---|---|
| `schemaVersion` | 清单格式版本 |
| `deviceId` | 稳定的内部 ID，不随展示文案改变 |
| `displayName` / `manufacturer` | 名称与厂家；未核实目标机型必须显示近似说明 |
| `verificationStatus` | `verified_reconstruction` / `partial_reconstruction` / `generic_approximation` |
| `assetVersion` / `assetHash` | 资产版本与内容校验 |
| `physicalDimensions` | 状态对应的有限正数、单位、是否包含相机凸起；不接受未知值偷偷归零 |
| `states[]` | 合拢、展开等静态状态 |
| `states[].modelPath` | 包内 GLB 相对路径 |
| `states[].screenBindings[]` | 屏幕内容节点、玻璃节点、材质槽与当前活动屏幕 |
| `states[].screenAspectRatio` | 模型真实有效屏幕比例，不从用户截图强行覆盖 |
| `states[].inputSizeHints[]` | 常见输入尺寸提示；包括用户指定测试尺寸，可标明为用户提供 |
| `states[].orientationPresets` | 横竖构图的根节点 / 相机调整，不等同于旋转截图文字 |
| `materialVariants[]` | 已实现且有依据的配色与材质 |
| `defaultPose` / `cameraFit` | 默认姿态与适配画布参数 |
| `attribution` / `approximationNotes` | 署名、来源说明与近似项 |

构建时对 GLB 内实际节点验证清单。任何必需节点丢失都必须使资产验证失败，不能“找不到就用第一个材质槽”。

### 14.2 可复现产物

模型生成器必须能从版本控制中的参数与脚本重新生成等价模型。不要让最终资产依赖没有记录的 Blender 手工操作或某个人电脑上的绝对路径。

参数变化需要有来源或修正理由。可保存 `.blend` 便于调试，但脚本与参数才是主要生产输入。若保留手工调整，导出回可追踪的数据或脚本，不留下不可复现步骤。

资产构建默认只在输入或工具链版本变化时执行；普通 Android Kotlin 代码修改不应每次重新建模和预计算所有环境。

### 14.3 需要实现的工具命令

**下面是要求 Agent 实现的 CLI 合同，不代表本说明文件已经附带这些程序。**工具应提供 `--help`、明确退出码、错误日志和幂等行为。

```bash
# 检查工具链和环境，不修改全局配置
python tools/doctor.py --json

# 根据已检索确认的公开 URL 拉取资料，生成台账和联系表
python tools/fetch_references.py --device xiaomi-18-fold

# 生成全部状态模型、材质和原创环境资产
python tools/build_assets.py --device xiaomi-18-fold --all-states

# 生成无隐私截图、色卡、坐标与透明测试输入
python tools/generate_test_images.py --output tests/fixtures

# 检查 schema、GLB、节点、纹理、单位、哈希与许可信息
python tools/validate_assets.py --all

# 检查实际生成的图片，不得自行伪造待检测导出结果
python tools/verify_exports.py --input deliverables/renders
```

Android 构建入口应采用已生成的 Gradle Wrapper。例如，实际模块创建后验证以下命令；若模块或任务名称不同，必须在 README 给出能直接执行的真实命令：

```bash
# macOS / Linux；Windows 使用 gradlew.bat
./gradlew test :app:lintDebug :app:assembleDebug

# 仅在已有已授权设备或可用模拟器时运行
./gradlew :app:connectedDebugAndroidTest
```

APK 输出路径由实际构建确认后复制到 `deliverables/apk/`，不能根据文件名猜测构建成功。

在 `build_assets.py` 内调用 Blender background 模式，并明确输入 / 输出路径与所需版本；不要把“打开 Blender，手工点这几个按钮”写成必须由用户执行的步骤。

下载工具允许读取 Agent 已填写的 URL 清单；不要求从零开发通用搜索引擎。Agent 自身的联网检索能力负责发现页面，工具负责可靠缓存、记录与再现。

## 15. 分阶段执行计划与完成门槛

按依赖推进，不需要每阶段向用户要批准。若支持子 Agent，可并行进行官方资料整理、模型脚本和 Android 工程研究，但主 Agent 负责统一坐标、数据合同、许可证和最终集成。不要并行创建互不兼容的第二套架构。

### M0：检查环境与建立项目

**工作：**检查工作目录和 Git 状态；选择不覆盖现有内容的项目路径；锁定工具链；写入简短 `AGENTS.md`；生成可构建 Android 工程；记录硬约束和本说明文件。

**产物：**`ENVIRONMENT.md`、`TOOLCHAIN.md`、Gradle Wrapper、最小 APK、`TASKS.md`。

**门槛：**现有环境允许时必须实际构建成功；不把没有执行过的编译命令写成已通过。存在环境限制时提供原始错误与已采取措施，并继续可以完成的资产工作。

### M1：官方资料与参数化初模

**工作：**按第 5–7 节自行找图、核对机型、测量主要尺寸，建立合拢 / 展开初模。此阶段允许灰模，但不是最终成果。

**产物：**来源台账、参考图联系表、`research.json`、`geometry.json`、两个 GLB、首轮轮廓对比图。

**门槛：**模型来源与估计项明确；屏幕 UV、机身厚度、两种状态与节点合同正确；GLB 校验零错误。

### M2：Android 三维渲染最短闭环

**工作：**将初模加载进 Filament；替换原创测试截图；实现真三维旋转；初步直接光 / 环境反射；按目标尺寸离屏导出。

**产物：**可运行 APK 和至少两张由 Android 渲染路径生成的 PNG。

**门槛：**截图映射、相机、资源生命周期和读回方向正确。**不得先做完完整 UI 才发现不能导出。**

### M3：模型与摄影光影打磨

**工作：**修正轮廓和倒角，完善可见结构，校准材质和三个光影预设；完成玻璃反射、柔和阴影、透明背景；比对官方外观。

**产物：**标准视角样张、机型对比说明、透明图在不同背景的检查图。

**门槛：**正面不变形、斜面有厚度、材质不是塑料玩具、反射随视角变化、透明无灰底。主视角不合格时优先修正这里，不增加外围功能掩盖问题。

### M4：完整编辑流程

**工作：**选图器 / SAF、完整显示与填满裁切、状态推荐、手势、角度面板、灯光 / 背景 / 画布、撤销、草稿和折叠屏布局。

**产物：**可从打开 App 一路完成保存分享的交互版 APK。

**门槛：**普通用户无需了解 3D 参数即可完成一张成片；编辑器旋转或折叠不会丢图与姿态。

### M5：导出与兼容性加固

**工作：**目标尺寸与透明通道测试、色彩测试、图像权限、模型快速切换、OOM 防护、前后台和原生库页面大小检查。

**产物：**多规格导出样张、测试日志、性能与内存数据、兼容性表。

**门槛：**实际跑过的用例有明确通过 / 失败；未有硬件条件的用例明确写未执行，不以模拟器结果代替真机结论。

### M6：交付整理

**工作：**清理示例垃圾、检查授权与隐私、更新使用 / 构建说明、生成校验值、汇总差距。

**产物：**见第 18 节完整目录。

**门槛：**除非明确说明环境阻塞，必须提供能安装的调试 APK，而非只提供项目骨架；文档说明精确到实际文件路径和实际命令。

## 16. 自动测试、视觉验收与实际证据

### 16.1 纯逻辑测试

覆盖适配比例、旋转方向、裁切边界、四元数归一化、相机适配、状态序列化 / 迁移、撤销合并和尺寸能力检查。

图像宽高为零、空 URI、损坏数据、异常 EXIF、超长图、同名不同内容、缺模型节点、过期工程版本都必须有防御处理。

### 16.2 资产测试

- 所有 GLB 经 glTF-Validator 检查，错误数为 0；警告逐项解释。[R13]
- 模型包围盒、单位、正面方向、活动屏幕唯一性、材质槽、纹理引用通过自动检查。
- 两状态使用相同机型参数体系，不出现展开后宽度与双机身结构明显不一致。
- 模型重建可复现；若二进制包含非确定元数据，用规范化结构与关键网格 / 参数校验，不强求无意义的文件字节完全相同。

### 16.3 导出测试矩阵

必须生成以下实际文件，名称可按工程统一规范调整：

| 用例 | 输入 / 场景 | 主要检查 |
|---|---|---|
| E01 | 1168 × 1712，外屏，正面，无反射 | 比例、四角、细文字和颜色 |
| E02 | 同输入，外屏，左右斜角 | 机身厚度、轮廓与动态反射 |
| E03 | 2364 × 1672，内屏展开 | 横向映射、无裂缝、无错误裁切 |
| E04 | 1672 × 2364，内屏竖向构图 | 文字方向正确、模型 / 相机转向正确 |
| E05 | 与屏幕比例不匹配的图片 | 完整显示不拉伸，填满模式裁切位置可控 |
| E06 | 透明背景，阴影关闭 | alpha 有效、边缘无黑白圈 |
| E07 | 透明背景，方向光接影 | 无矩形底板，阴影随姿态变化 |
| E08 | 2160 × 3840 与 3840 × 2160 | 精确像素尺寸，不是预览放大 |
| E09 | 反射 0 / 默认 / 较强 | 参数有效，默认文字仍清楚 |
| E10 | 纯色、渐变与深背景 | 背景与预览一致，没有反向 / 色带异常 |
| E11 | 连续替换截图再导出 | 导出最后选择的图片，没有旧纹理 |
| E12 | 导出期间继续修改场景 | 导出采用冻结快照，工程状态未损坏 |

没有条件实际生成的文件不能用 Blender 渲染伪装为 Android 导出。

### 16.4 色彩验收方法

使用含中性色块、饱和色块、灰阶与小字号文字的原创测试图。将屏幕正对相机，关闭反射与额外调色，在避开边缘和文字抗锯齿的位置采样。

记录源图与导出图的 RGB 差异；有可用工具时计算转换到同一色彩空间后的 ΔE2000。清晰模式以平均 ΔE2000 不超过约 3 为初始目标，超过则定位 gamma、曝光、tone mapping 或编码问题。这个阈值是项目目标，不是已经实现的效果保证。

不要用带强反光的透视成片来测“像素级原色”，也不要用截图文件整体 hash 判断颜色是否正确。

### 16.5 透明验收方法

程序检查 PNG 有 RGBA 通道、画布空白处 alpha 为 0、机身主体主要区域不透明、边缘含合理过渡。将输出分别合成到白、黑、饱和背景，保存检查图。

重点检查：透明边缘黑圈、白色描边、玻璃区域发灰、阴影平面矩形、细缝漏色、Y 翻转和 RGB 通道错位。alpha 数值通过不等于视觉通过，必须查看图像。

### 16.6 预览与导出一致性

同一场景状态下比较构图包围盒、设备中心、主要角度、颜色块和阴影方向。允许因分辨率与抗锯齿带来的微小差异，不允许导出改变镜头、裁切或光照。

自动回归基线需注明 GPU / 后端。不同 GPU 不要求逐像素一致；用容差指标和视觉检查，而不是大量误报的绝对图片 hash。

### 16.7 UI 与生命周期测试

至少验证：首次安装、无权限导入、取消选图、切换横竖屏、窗口变窄、内外屏切换、应用后台恢复、强制结束后恢复草稿、存储不足模拟、分享返回、模型加载失败。

窗口测试覆盖约 360 dp 宽手机、较宽外屏、600–840 dp 档位和更大窗口；这些是布局测试规格，不用用户屏幕像素直接代替 dp。

模拟器能够验证布局和基本渲染，但不能用于宣称真实小米 GPU 性能、色彩或系统图库行为已通过。

### 16.8 视觉自检循环

按“生成样张 → 实际查看 → 标注问题 → 修改参数 / 材质 → 再生成”迭代。至少完成一个有问题记录与修正前后对照的循环。

必须查看以下局部：屏幕四角、前玻璃与边框接缝、斜角中框高光、铰链、相机凸起、投影接触位置、透明边缘。没有视觉工具时可以做数值与图像输出，但报告必须标记“未完成视觉人工 / 模型查看”，不能声称主观质感已验收。

## 17. 风险与默认处理方案

| 风险 | 默认处理 |
|---|---|
| 官网参数不全 | 官方数值与估计分离；参数化近似继续开发，不求用户找模型 |
| 官网链接返回另一商品 | 核对页面主体身份，重找实际产品入口；不沿用搜索摘要 |
| 手机外观太像通用盒子 | 优先修正轮廓、边框、倒角、相机与铰链，不靠加大阴影掩盖 |
| Blender 很漂亮、Android 很差 | 以 Filament 实际成片为最终标准，使用可移植材质与运行时校准 |
| 屏幕发灰或过曝 | 先关闭玻璃与调色，检查 sRGB / 线性链路，再逐项恢复效果 |
| 透明导出黑边 | 验证读回与 Bitmap / PNG alpha 表示及清屏 RGB，禁止盲目重复解预乘 |
| 玻璃层闪烁 / 穿模 | 调整真实尺度、深度写入、表面偏移和排序；先用无折射表面反射 |
| 图像替换后内存上涨 | 追踪 Buffer、Bitmap、Texture 和 gltfio 所有权，去掉无界缓存 |
| 材质编译版本不匹配 | 将工具和 Android 依赖固定为匹配版本，重建材料包 |
| 模拟器渲染失败 | 保留错误、尝试支持的后端 / 架构；继续源码、资产和构建检查，不冒充真机验证 |
| 4K 导出 OOM | 导出前能力判断、单任务、释放临时资源；提示更低尺寸，不静默作假 |
| 开发范围膨胀 | 只保证一个小米折叠机、两状态、静态图完整体验；视频 / 多机型后置 |
| 无法确认资产再分发许可 | 改用原创环境与自建几何；未知资产不进入 APK 和公共仓库 |
